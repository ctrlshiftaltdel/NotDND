## 0. 怎么用这份文档

### 0.1 三条使用路径

| 你手里的事 | 走哪条路 |
|---|---|
| 为某个**已确定**的资产槽位写提示词 | 按 §4 模板在本文件**新增一条记录**（交付物类型 `image_prompt_authoring`，建议 `@promptor`） |
| 把写好的提示词交给外部模型**出图 / 挑图** | 在**仓库外**完成（`external_image_generation`，**不派发**给任何 Subagent）；状态转 §6 的「待用户生成」 |
| 把候选图片变成**正式资产** | **另立**资产导入 Issue / PR（`code_implementation`）；批准与验收口径见 §8 与 `UI-DESIGN.md` §4.5 |

### 0.2 一条记录的生命周期（一眼版）

```text
提示词待编写 → 提示词已完成 → 待用户生成 → 待审核导入 → 已批准导入 → 已导入并验证
                                                   ↘ 阻塞（槽位 / 规格 / 风格未定，或依赖未合入）
```

状态词表与「谁能设置」见 §6。**没有合并后的图片文件与清单键，任何记录都不得写
「已导入并验证」**；**没有图片时不得写「已生成 / 已验证」**。

### 0.3 本文件不做什么（红线）

- **不生成图片**：本文件只有文字。实际出图由**用户**在仓库外选择模型完成
  （`AGENTS.md` §3.1）——`@promptor` 只交付**提示词文档**，**不得**把提示词产出写成 / 说成图片产出。
- **不改运行时契约**：不定义 / 不修改资产槽位、文件名与 `static/assets.json` 映射；
  运行时**不得**读取本文件（无构建步骤、无运行时解析，`UI-DESIGN.md` §0.2）。
- **不构成批准**：写进清单 ≠ 批准入库。批准只看 GitHub 上**资产导入 Issue / PR 的合并**（§8.2）。
- **不夹带密钥与隐私**：不记录 API Key、私有端点、账号、本机路径、私密会话记录
  （`AGENTS.md` 铁律 3）。
- **不借清单扩权**：新增 / 修订记录不得扩大任何 Issue 的允许路径；确需跨类改动走
  `AGENTS.md` §9 的正规申请路径。

## 1. 清单总则

### 1.1 这份文件是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 「要生成什么 / 如何生成」的**文本规格**——每条记录独立可读，可直接交给外部图像模型 | **资产文件本身**：本文件不含、也不链接任何图片 |
| **待制作素材的提示词清单**（人读、审查、复用） | **运行时资产清单**：那是 `static/assets.json`（槽位键 → 同源路径） |
| 槽位 / 路径 / 规格 / 验收的**引用表** | 槽位与路径的**定义者**：定义权在 `UI-DESIGN.md` §4.3 与资产导入 Issue |
| 状态与关联 Issue 的**索引** | 批准凭证、模型会话记录或提示词日志（本仓库**不要求**存这些） |

### 1.2 谁写、谁生成、谁批准

| 环节 | 谁做 | 产物 | 边界 |
|---|---|---|---|
| 编写 / 修订提示词 | `@promptor`（`image_prompt_authoring`） | 本文件的记录 | 只交付**提示词文档**；不生成图像、不导入图片、不改生产代码或资产映射、不擅自发明运行时槽位 |
| 实际出图与挑图 | **用户**（OpenCode 之外，`external_image_generation`） | 候选图片文件 | **不派发**给任何 Subagent；模型选择与参数在仓库外 |
| 批准与入库 | **独立**的资产导入 Issue / PR（`code_implementation`） | 图片文件 + `static/assets.json` 键 | 必须**提前**列明范围与验收（`UI-DESIGN.md` §4.5「导入前置」） |
| 接线与回退验证 | `@builder` | 占位 / 加载 / 回退证据 | 缺图**不阻塞**主功能（D2 占位先行） |

> 两套东西不要混：`能力：设计` 之类的标签只说明**谁适合做**，**不等于**「能生成图片」；
> **提示词编写 ≠ 图片生成**（`AGENT-ORCHESTRATION.md` §1.5）。

### 1.3 三类素材与入库边界

口径由 `GDD-BASELINE.md` §2「D2 实施边界」与 `UI-DESIGN.md` §4.5 决定，本文件只**引用**：

| 类别 | 含义 | 入库方式 | 在本清单里的记录要求 |
|---|---|---|---|
| ① 必要 **UI chrome** | 不随世界 / 故事变化的界面部件（框架 / 面板 / 边框 / 图标 / 控件状态） | 随该 UI 实现 / 修复 PR 审 | 优先 CSS / 内联 SVG；只有 UI 单明确要一份**原创、本地、可随仓库交付**的静态素材时才登记；**不得**把控件 / 边框 / 面板做成不可访问的**整块位图** |
| ② 正式**世界 / 故事资产** | 角色肖像、场景图、物品图、地点图 | **独立**资产导入 Issue / PR | 记录必须引用已批准的槽位与路径；未批准一律标「待确认」（§3.1） |

## 2. 槽位、命名与规格（引用既有契约，不发明）

### 2.1 槽位与类别

槽位（资产位）是**设计概念**，不是文件：`<类别>/<实体 id>`，全小写 ASCII + `-`
（`UI-DESIGN.md` §4.3）。类别与实体来源：

| 类别 | 槽位形状 | 实体来源（示例） |
|---|---|---|
| `portrait` | `portrait/<角色 id>` | 剧本 NPC id（对白拍的 `speaker`），如 `npc-01` |
| `scene` | `scene/<剧本>-<地点>` | 剧本地点 id，如设计文档示例 `scene/yunji-loc-02` |
| `item` | `item/<物品 id>` | 物品 / 奖励（`granted` 里的名字） |
| `place` | `place/<world_key>/<place_id>` | ATLAS 地点，如 `place/emberfall/cliff-station`（`static/assets/README.md` 示例） |

> 上表「示例」只说明**形状**，不代表这些位已有正式资产。**新增槽位必须由资产导入 Issue
> 批准**，本清单无权发明（`AGENT-ORCHESTRATION.md` §1.5 任务包契约第 1 项）。

### 2.2 路径与文件名

| 项 | 口径（出处：`static/assets/README.md`） |
|---|---|
| 目录布局 | `static/assets/<类别>/<实体 id>.<扩展名>`；`place` 为 `static/assets/place/<world_key>/<place_id>.<扩展名>` |
| 文件名 | 全小写 ASCII 字母 + 数字 + `-`（与 `AGENTS.md` §7 一致）；不得与其他素材冲突 |
| 扩展名 | 首选 `.webp`；`.jpg` / `.png` 也认 |
| 来源 | **只接受同源路径**——图床 / CDN / 临时会话 URL 一律不行（`UI-DESIGN.md` §0.2 零外链） |

### 2.3 规格上限

| 类别 | 像素上限 | 宽高比 | 单文件 |
|---|---|---|---|
| `portrait` / `item` | 512×512 | 1:1 | ≤ 400 KB |
| `scene` / `place` | 1280×720 | 16:9 | ≤ 400 KB |

> 透明背景、裁切余量等**未在本表固定**的规格，属素材级决定；须由资产导入 Issue 写明，
> 未写明时在记录里标「待确认」（§3.1）。

## 3. 「待确认」与索引表

### 3.1 槽位 / 路径未定时怎么写

清单只**引用**已批准或已存在的槽位与路径。**不得**为填满字段而猜一个 id 或路径：

| 情形 | 记录里怎么写 |
|---|---|
| 槽位已存在 / 已批准 | 直接写槽位，如 `place/emberfall/cliff-station` |
| 槽位尚未批准（形状可知） | 写 **待确认**，并附上「拟用形状 + 需要哪条 Issue 批准」（如：待确认——拟用 `portrait/<npc id>`，需资产导入 Issue 批准） |
| 目标路径未定 | 写 **待确认**（走 §2.2 口径，不另造目录） |
| 关联 Issue 尚无 | 填 `—`，并说明依赖哪条资产导入 Issue；**不得**编造 Issue 编号（`AGENTS.md` §4 / §7） |

解除条件：拿到对应资产导入 Issue / PR 的批准后**回填**，并在「关联 Issue」列写明依据
（`PR #N（Issue #M）` 格式，`AGENTS.md` §7）。**未批准的槽位不得写进 `static/assets.json`。**

### 3.2 索引表（模板；当前为空）

> 空表是**合法状态**：还没有任何素材需求被登记。缺图不阻塞运行——界面继续用几何占位
> （`UI-DESIGN.md` §4.2 / §4.4）。

| 序号 | 槽位 / 资产 ID | 名称 · 文件名 | 类别 | 世界 / 风格 | 目标路径 | 状态 | 关联 Issue |
|---|---|---|---|---|---|---|---|
| — | — | — | — | — | — | — | — |

**维护规则**：

- 一行 = 一个槽位 = 一个记录小节（记录追加到 §10「素材记录」区末尾，索引表始终在前，便于扫描）。
- **序号**（`A-001` 起）只是本文件的记录键，**不是**资产 ID / 槽位，

## 5. 提示词写法（模型中立）

### 5.1 语言与可复制性

- **主体提示词优先英文**；同时保留**中文用途 / 设计意图摘要**（Issue #307 口径）。
- 提示词放在 fenced `text` 代码块里，**整段可复制**；不用「它」「上面那张」这类指代。
- **每条素材都要有独立主提示词**——共用规范写进「一致性约束」并在主提示词里**复述**，
  不得只写「同上」（§5.4）。

### 5.2 主提示词的结构

按下列顺序写，缺项要么补齐、要么在记录里写明「不适用」：

1. **主体**——谁 / 什么，含可辨识特征（区分同组其他素材）；
2. **动作 / 姿态 / 表情**——简单、稳定，避免会让模型跑偏的复杂动作；
3. **环境 / 背景**——与该世界的母题一致；需要后期裁切或抠图时说明背景处理期望；
4. **构图与视角**——镜头距离、平视 / 俯视、主体在画面中的占位比例；
5. **光线**——光源方向、时间感、明暗对比；
6. **色彩与材质**——引用世界主题的色族与材质语言（`UI-WORLD-THEMES.md` §3）；
7. **细节层级**——前景 / 中景 / 背景的信息密度（显示尺寸极小，避免满屏细节）；
8. **预留裁切空间**——安全区（肖像留头顶与两侧；场景 / 地点避开边缘与 UI 叠层区域）。

> 只描述**视觉要素**：**不点名**在世艺术家、工作室、品牌、具体作品或版权角色，
> **不要求**模仿特定版权角色 / 世界（§7.1）。风格用可观察的词汇描述
> （如「手绘感」「低饱和矿物色」「平涂 + 细描边」）。

### 5.3 可选负面提示词

- 负面块是**可选项**；**不能假设**所有图像模型都支持独立 negative prompt。
- 模型不支持独立负面字段时：**保留**负面清单（供人工挑图时逐条核对），
  **不强行改写**主提示词——主提示词必须删掉负面块后仍完整可用。
- 负面清单写**类别**而不是套话堆砌，例：水印 / 签名、乱码文字、品牌标识、多余肢体或手指、
  拼接缝隙、低分辨率伪影、透明区白边或棋盘格残留、外链元素与二维码（§7.2）。

### 5.4 一致性约束

同一世界 / 同组素材共用一份规范，写清这几项并**在每条主提示词里复述关键点**：

| 维度 | 例（按所选世界主题取值） |
|---|---|
| 色温与色族 | 奇幻篇旧金 / 苔绿；现代篇冷蓝 / 石墨；未来篇冷青 / 深空蓝黑（`UI-WORLD-THEMES.md` §3） |
| 材质与笔触 | 低饱和矿物色、平涂 + 细描边，或写实材质的统一处理 |
| 镜头与景别 | 肖像统一平视半身；场景统一 16:9 广角 |
| 轮廓重量 | 有无描边、描边粗细一致 |
| 细节密度 | 显示尺寸下可读，不堆细节 |
| 背景处理 | 纯色 / 简洁背景或统一的环境处理 |

### 5.5 模型适配备注：写什么、不写什么

| 可写（模型差异） | **不可写** |
|---|---|
| 目标宽高比与像素（对照 §2.3） | 模型 / 服务**品牌**与其专属参数语法 |
| 是否需要透明背景 | API Key、令牌、私有端点、账号 |
| 是否支持独立 negative prompt | 本机路径、个人目录、内网地址 |
| 出图后的通用需求（裁切、放大、统一色温） | 模型会话记录、会话 URL、私密提示词日志 |

原则：**主提示词保持通用可搬运**；差异只进备注，**删掉备注后主提示词仍可独立使用**。
本清单**不记录**模型配置，也**不接入**任何图像生成 API（`AGENT-ORCHESTRATION.md` §1.5）。

## 6. 状态词汇与流转

| 状态（中文） | ASCII 标记 | 含义 | 谁能设置 |
|---|---|---|---|
| 提示词待编写 | `PROMPT_TODO` | 槽位 / 用途已登记，提示词尚未写 | `@promptor`（登记时） |
| 提示词已完成 | `PROMPT_READY` | 提示词自包含、可交给外部模型；**不代表图片已生成 / 已审核 / 获准入库** | `@promptor` |
| 待用户生成 | `AWAITING_GENERATION` | 已交用户，在仓库外选模型出图 / 挑图 | 用户；`@promptor` 可依用户回执转记 |
| 待审核导入 | `PENDING_IMPORT_REVIEW` | 候选文件已提交资产导入 Issue / PR 审核 | 提交者（用户或该 Issue 的执行者） |
| 已批准导入 | `APPROVED_FOR_IMPORT` | 资产导入 Issue / PR **已批准**这批文件与槽位；**未合并前仍不是正式资产** | **只能**由资产导入 Issue / PR 的授权流程确认——**`@promptor` 不得自行设置** |
| 已导入并验证 | `IMPORTED_AND_VERIFIED` | 图片文件与清单键已合并，显示 / 回退证据已记录 | 资产导入 PR 的交接记录（合并后） |
| 阻塞 | `BLOCKED` | 槽位 / 规格 / 风格未定，或依赖未合入 | 发现者；必须写明**原因与恢复条件** |

**纪律**：

1. 只沿上图**单向推进**，不跳级。允许回退（如资产被驳回、规格变更），但必须写明原因与
   新的恢复条件。
2. **没有图片时**不得标「已生成 / 已通过审核 / 已导入并验证」——`PROMPT_READY` 只说提示词可用。
3. **「提示词已写好」「模型已生成」都不是入库理由**；只有合并后的**文件 + 清单键**才算正式资产
   （`UI-DESIGN.md` §4.5）。
4. 本词表只描述**素材记录**，不是任务编排状态机；任务状态（`READY` / `DISPATCHED` 等）
   以 `AGENT-ORCHESTRATION.md` §2 为准，两者**不得混用**。

## 7. 原创性与禁止内容

### 7.1 原创性（`AGENTS.md` 铁律 1 同源）

提示词与生成结果都应为**原创**：

- **不**复制 / 翻译 / 改名 / 微调第三方受版权保护的表达；**不**照抄他人提示词文本；
- **不**仿冒品牌、商标或冒充第三方产品；
- **不要求**生成模型模仿特定版权角色 / 世界，也不点名在世艺术家；
- 记录里只保留完成审查所必需的原创性与素材清单信息——**不要求**仓库存私密提示词日志或模型会话记录。

### 7.2 禁止内容（可复用清单）

| 类别 | 例 | 为什么 |
|---|---|---|
| 标记与出处 | 水印、签名、图库编号 | 破坏原创性说明，也污染画面 |
| 文字 | 随机 / 不可读文字（招牌、书页、界面文案） | 需要文字时必须在记录里给出**确切字符串**，否则要求「无文字」 |
| 品牌 | 商标、品牌标识、仿冒 logo | 铁律 1 |
| 未授权素材 | 第三方受版权角色 / 世界、现实人物肖像 | 铁律 1 |
| 构图冲突 | 与接入点冲突的元素（叙事流正文插图、把占位几何样式烘进图片） | 接入点口径（`UI-DESIGN.md` §4.3） |
| 低质伪影 | 多余肢体、熔脸、拼接缝、贴纸白边、透明区棋盘格残留 | 验收标准不可过 |
| 外链与可扫描码 | 二维码 / 条形码 / URL 文本 | 零外链（`UI-DESIGN.md` §0.2） |
| 基调 | 与本产品基调不一致的内容（露骨性内容、过度血腥） | 内容边界 |

## 8. 验收标准与入库接口

### 8.1 记录里的验收标准（每条必填、逐条可勾选）

- [ ] **主体可辨识度**：缩到实际显示尺寸（队伍面板肖像约 56px，
      `static/assets/README.md` 接入点表）仍能认出主体与区分特征；
- [ ] **构图与安全裁切区**：主体不贴边；按目标宽高比留出裁切余量；
- [ ] **边缘 / 透明度**：需要透明时四角干净、无白边或残影；不需要时边缘无缝隙；
- [ ] **尺寸与格式**：对照 §2.3（像素、宽高比、扩展名、单文件 ≤ 400 KB）；
- [ ] **一致性与原创性**：与同组素材共用规范一致；无可识别的第三方版权元素；
- [ ] **显示与回退**：有图时渲染成图；删图 / 断链 / 清单缺键时退回几何占位且不阻塞主功能
      ——证据由**资产导入 PR** 提供（§8.2）。

### 8.2 资产导入 Issue / PR 的最低验收信息（引用，不复制口径）

下列五项由**资产导入 Issue / PR**逐项提供，缺任一项视为**未验证**
（权威表述见 `UI-DESIGN.md` §4.5 与 `GDD-BASELINE.md` §2「D2 素材生产与入库口径」）：

1. 新增图片的**路径**（逐个列出，或 `git diff --name-only`）；
2. **格式**与**尺寸**（实际像素，并说明 16:9 还是 1:1）；
3. 对应的**资产 ID / 槽位**——供图时**必须**与 `static/assets.json` 的键核对一致；
4. **来源说明**：经外部模型生成、并由**用户选择 / 审核**（写明依据哪一批资产导入 Issue / PR 的批准）；
5. **显示与回退验证证据**（有图渲染成图；删图 / 断链 / 清单缺键退回几何占位）。

> 本文件的状态列**不代替**上述验收；**不得**用外链、临时 URL 或本清单**代替**图片文件。

## 9. 常见错误（反例 → 正确做法）

| 反例 | 为什么不行 | 正确做法 |
|---|---|---|
| 第二条只写「同上」 | 记录必须独立可读、可复制 | 复述共用规范，写独立主提示词（§5.1 / §5.4） |
| 未批准的槽位直接写进 `static/assets.json` | 槽位与映射不在本清单权限内 | 标「待确认」，走资产导入 Issue（§3.1） |
| 把 `demo-` 样张登记成正式槽位 | 违反三类素材的隔离口径 | 类别写「③ 隔离测试·原型样张」，槽位保留 `demo-` 前缀（§1.3） |
| 提示词里写模型专属参数（权重语法、特定开关） | 绑定单一模型，破坏可搬运性 | 移到「模型适配备注」或删掉（§5.5） |
| 记录 API Key / 私有端点 / 本机路径 | 违反铁律 3 | 一律不记录；只写变量名或通用能力（§5.5） |
| 提示词点名在世艺术家 / 版权角色求相似 | 违反铁律 1 | 改写成可观察的视觉要素（§5.2 / §7.1） |
| 还没出图就标「已生成 / 已导入并验证」 | 状态造伪，误导审查 | 按 §6 推进；`PROMPT_READY` 只说提示词可用 |
| 自行把状态写成「已批准导入」 | 批准只属资产导入 Issue / PR | 等授权流程确认后再回填（§6） |
| 把索引表与小节写成两套 | 清单不可维护 | 序号一一对应，先修清单再写提示词（§3.2） |
