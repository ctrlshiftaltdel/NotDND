# NotDND 六角格战棋战斗系统：完整分阶段研发方案

> **文档地位**：本文件是 M13 六角格战斗的**研发路线与架构方案**，不是规则契约。
> 规则数值与空间契约以 **Issue #415** 与 `docs/system/02c-hex-battlefield.md` 为准；
> 数据 Schema 以 `#416` 落地的 `data/schema/*tactical*.schema.json` 为准。
> 文中第 3 节的 JSON 是**形状示意**（原文已注明），不得直接照抄为最终 schema。
> Issue 切片映射见 **#430**（M13 总跟踪）。

- 项目：`ctrlshiftaltdel/NotDND`
- 方案基线：`master`，审查基准提交 `e82b3f21559271ddf0b9c56fe06b2a1c153ab50f`（2026-10-19）
- 状态：研发方案；已入库；Issue 切片见 #430（M13 总跟踪）
- 核心目标：把战斗升级为可操作的六边形格（Hex）战棋，支持真实高度差、地形、建筑、障碍、掩体、机关和道具交互，同时完整保留 NotDND 既有世界设定、战斗规则复杂度及两个规则引擎。

> 本方案将“6格战棋”按“六边形格（Hex）战棋”理解：每个格子有六个水平邻接方向，并非整张地图只允许六个格子。首版使用可点击的六角格棋盘与高度分层表达，不要求先拥有正式美术或完整 3D 渲染。

---

## 1. 成品目标与不可妥协原则

### 1.1 玩家最终应该获得的体验

1. 战斗开始时，系统生成或载入一张有边界的六角格战场，显示地面、高低台、楼梯、平台、墙壁、掩体、危险区域、机关和可交互物件。
2. 我方角色、敌人和必要的中立单位都在战场上拥有权威坐标；界面展示其位置、朝向（若规则使用）、活力、韧性、状态、行动资源和关键能力。
3. 玩家可选择单位、查看可移动范围、选择目标格、选择敌人或物件并发起行动。系统在服务端验证行动是否合法、所需资源、距离、视线、高度、遮挡及目标状态。
4. 高度差不是装饰：它能够按数据规则影响移动、射程、视线、掩体、高地优势、坠落、攀爬和环境效果。
5. 战场对象不是只有图片。对象有类型、位置、占位、状态和规则效果；玩家可绕行、攀爬、破坏、启动、关闭、拾取或利用它们，具体能力由对象类型决定。
6. 现有的攻击分档、伤害、抗性、状态、韧性/破韧、首领阶段、连携、招式、遭遇预算和撤退等规则继续生效。战斗地图不能把系统简化成“移动一格、攻击一次”的浅层玩法。
7. `tactics`（战术骰）和 `build`（构建骰池）继续使用各自规则。空间、地图和交互可以共享；命中、伤害与能力结算通过各自适配层完成，不强行合并成一套公式。
8. 先使用几何图形、符号、颜色和现有 UI token 做出可玩的版本。正式图片、动画和特效后置；素材缺失不影响判定和存档。
9. 服务器是战斗事实唯一来源。前端只负责显示与提交意图，不能自行决定伤害、合法移动、回合、胜负或战场对象最终状态。
10. 浏览器刷新、断线恢复和多人同步后，战斗状态必须一致；重要行动应可追踪、可测试、可重放。

### 1.2 首版不要求的内容

- 不要求实时物理、刚体碰撞、布料、真实弹道模拟或完整 3D 游戏引擎。
- 不要求第一阶段就有精细角色动画、全套插画或特效。
- 不要求所有战斗必须使用固定大小的网格；地图尺寸、格子尺度、单位占位和可用对象应由场景数据决定。
- 不替换世界级 ATLAS 地图，也不把自由探索强制改成战棋移动。
- 不把自由文本叙事、AI 导引者和规则判定混为一体。AI 可以提出意图、生成战斗演出与 NPC 计划，数值结算必须走权威规则。

### 1.3 当前实现可复用与缺口

可复用基础：

- `prism_core.py`：战术攻击、伤害、韧性、先攻、遭遇、敌方行动、胜负检查、构建骰池相关规则，以及可选的 ATLAS 战术投影函数。
- `atlas.py` / `atlas_gen.py` / `atlas_compile.py`：世界/地点/房间图、连接、空间层级、可达性、战术区域投影和场地要素生成。
- `data/system/combat.json`、`data/system/tactics_combat.json`、`data/system/tactics_encounter.json` 及相关 Schema：既有战斗规则来源。
- 现有 `ACTION-DESIGN.md`、状态/事件提交框架、`notdnd_web.py` 服务端和原生 JS 前端。
- `static/assets.json`、`static/js/ph.js` 与资产目录：可复用作占位及正式素材替换框架。

需要新增或补齐：

- 独立的战斗尺度六角格战场模型；ATLAS 的世界地点连接不能直接替代格内战术地图。
- 单位/对象在六角格上的真实坐标和高度，路径规划、占位、地形成本、视线、射程与遮挡计算。
- 战场对象的结构化效果、状态机和权威交互结算。
- 战斗 API 与 UI 的端到端接线。当前可见代码有规则引擎和空间函数，但没有形成完整的网页战斗地图、战斗专用操作流及服务端生命周期闭环。
- 敌人基于位置、地形、射程、危险和目标的战术行动选择。
- 战斗地图/单位/对象的保存恢复、事件回放和多人同步。

## 2. 总体架构建议

建议保持现有模块职责分离，新增“战术战场层”，不要把所有逻辑塞进 `prism_core.py` 或前端脚本。

```text
World modules / Scenario / ATLAS world map
                 |
                 v
       Battle-map builder / template
                 |
                 v
      Tactical battlefield model
     (hex cells, elevation, units,
      obstacles, cover, hazards, props)
                 |
       +---------+---------+
       |                   |
       v                   v
Movement / spatial      Battle action validator
queries                 (target, range, LOS,
                         AP/resources, state)
       |                   |
       +---------+---------+
                 v
       Combat rules adapter
        /              \
  tactics engine      build engine
        \              /
                 v
     Authoritative state/event commit
                 |
                 v
       Combat API / snapshot / log
                 |
                 v
    Hex-grid UI / touch / status panels
```

### 2.1 职责边界

- **ATLAS**：负责世界尺度的区域、地点、楼层、房间、连接、生成与可达性；为战斗提供地点、种子、设定上下文和场景入口。
- **战术战场层（建议新增独立模块，例如 `tactical_battlefield.py`）**：负责六角格坐标、格子属性、高度、单位占位、对象位置、路径成本、可达区域、战场局部几何、视线和射程查询。不负责最终决定攻击命中和伤害。
- **PRISM 规则适配层**：把战术上下文（距离档、高地、掩体、遮挡、目标位置、环境效果）交给当前战术引擎或构建引擎；继续使用其既有命中、伤害、状态与资源规则。
- **战斗编排/服务端**：处理开始/结束战斗、回合状态、行动验证、幂等、版本冲突、状态提交和事件记录。战斗操作需要进入现有权威状态/事件提交约束，不能形成一条不受审计的旁路。
- **前端战场视图**：展示服务器状态、选择格子/单位/对象、提出行动请求、显示预览；不得直接写入战斗事实。
- **表现资产**：通过资产 manifest 槽位加载；缺失时回退至几何占位。图像不能决定碰撞、视线或规则效果。

### 2.2 保留 ATLAS 与战斗地图的双尺度

世界地图与战斗地图是不同尺度、不同用途的数据：

- 世界地图：区域、建筑、房间、道路和跨地点旅行；维持当前 ATLAS 图结构。
- 战斗地图：一个遭遇内的六角格布局，通常对应一个房间、街区片段、洞穴、屋顶、桥梁或战场区域。

建议从当前 ATLAS 房间与其 `features` 生成战斗地图草案，但使用明确的战场模板/生成器创建六角格；不能简单将一个 ATLAS `zone` 当作战棋格。战斗结束后，重要破坏、开启/关闭、警报和地形改变通过事件回写场景/世界状态。

## 3. 核心数据模型

在写前端前先定数据契约，并写 schema 与迁移测试。字段名可在设计阶段最终定稿，但模型至少要覆盖以下内容。

### 3.1 战场 Battlefield

```json
{
  "schema_version": 1,
  "battlefield_id": "battle-...",
  "source_scene_id": "...",
  "seed": 12345,
  "grid": {
    "type": "hex",
    "coordinates": "axial",
    "orientation": "pointy-top",
    "cell_scale": 1,
    "height_scale": 1
  },
  "cells": [],
  "units": [],
  "objects": [],
  "links": [],
  "visibility": {},
  "revision": 0
}
```

这是形状示例，不是要求原样照抄的最终 JSON。正式 schema 应把每个子结构限制为显式字段，避免任意自由键在不同模块产生歧义。

### 3.2 六角格坐标与高度

- 使用轴向坐标 `q, r`（第三轴 `s = -q-r` 可按需派生），六个水平相邻方向由一个固定常量表定义。
- 每格保存整数 `elevation`/高程层级；如果需要桥面、地板和地面在同一水平投影下共存，另加明确的 `surface_id` / `layer_id`，不得把所有高度信息压成一个二维坐标。
- 统一实现 `hex_distance(a,b)`。标准水平六角格距离为 `max(abs(dq), abs(dr), abs(dq+dr))`；带高度的实际距离与攻击范围采用规则配置，禁止各模块自行写不同公式。
- 战场边界由实际存在的 cell ID 决定；空洞、墙体、悬崖和地图外部不是同一种情况。
- 世界/战斗单位的“米数”与格数转换由战场规则配置决定；ATLAS 当前的“一区约 6 米”不能不经核对就直接视为战棋格尺度。

### 3.3 Cell / 地形格

每格至少包含：

- 唯一 ID、`q/r`、高程、表面/层级；
- `terrain_type`、基础移动成本、是否可站立；
- 移动阻挡、视线阻挡、透明度/遮挡类别；
- 掩体基础属性、危险/表面效果 tag；
- 允许的移动模式（步行、攀爬、飞行、游泳等，可按能力/场景配置）；
- 来源、是否被发现、是否可破坏/可变化；
- 视觉槽位（可选，缺失不影响规则）。

### 3.4 Unit / 单位战场状态

每个玩家、NPC 或敌人应有独立的战斗位置映射，而不是把战斗位置临时塞进叙事文字：

- `unit_id`、阵营、当前格、所处层/表面、高度/体型与占用 footprint；
- 可选朝向（只有需要背袭、扇形技能、盾牌朝向时才参与规则）；
- 现有权威角色状态引用：活力、韧性、状态、装备、抗性/弱点、战斗资源；
- 当前回合 AP/动作额度、反应次数、移动剩余量、技能冷却（若规则已有此概念）；
- 移动模式/攀爬/飞行/涉水能力；
- 濒危、死亡、被束缚、击退等状态必须复用既有状态语义，不另造同名状态。

多人局中，角色主体与玩家权限仍由现有会话/房间机制管理；不能把客户端发来的 `unit_id` 当作权限证明。

### 3.5 Battlefield Object / 战场对象

对象应按类型拥有明确的行为，不做一个大而无当的万能对象：

- **阻挡物**：墙、石柱、不可通行残骸；影响可达性和视线。
- **掩体**：矮墙、沙袋、车辆、桌柜；提供不同档位防护，可损坏或改变状态。
- **危险区域**：火焰、酸池、带电水面、烟雾、毒雾、坍塌地板；有覆盖范围、触发时点、伤害/状态与持续时间。
- **机关**：开关、拉杆、吊物、警报、门锁、结构柱；有交互条件、成本、成功结果、状态转换与后果。
- **可移动/可破坏物**：货架、桶、箱、爆炸罐；有占位、耐久、重量/移动规则和被破坏后的状态。
- **可拾取物**：掉落装备、钥匙、补给、证据或剧情道具；交互后进入正确的权威库存/任务系统。
- **垂直通路**：楼梯、梯子、绳索、坡道、电梯、跃迁点；为高程层之间提供显式转换规则。

对象至少应支持状态标记、占位/覆盖范围、可交互动作、触发机制、状态变化、权威效果及事件记录。不是所有对象都必须可破坏或可移动。

### 3.6 双引擎适配原则

- 战术引擎继续调用现有的 d20 命中分档、伤害、抗性、失手、韧性与状态规则。
- 构建引擎继续调用现有骰池成功数、闪避需求、溢出效果、动量与过载规则。
- 共享层提供的是位置与环境事实，例如“目标距离 4 格”“射线经过中度掩体”“攻击者高于目标 2 层”“路径经过危险格”。
- 各引擎适配器负责把这些事实转换成已有规则认可的修正/结果；凡要新增数值公式，都须先修订对应规则设计文档和数据，不得只在代码里藏常数。

## 4. 分阶段研发路线

## 阶段 0：规则盘点、架构冻结与战斗规格定稿

**目标：** 在写代码之前，明确“六角格、高程、旧规则、动作经济、敌人回合”之间的契约，避免实现到一半才发现现有规则互相冲突。

### 工作项

1. 审核并建立既有战斗规则清单：攻击等级、暴击与失手、伤害类型/抗性、活力、韧性与破韧、首领阶段、连携、动作点、反应、异常状态、撤退、遭遇预算、两种引擎的独立机制。
2. 将战场相关规则标记为：已实现且可复用、已定义但仅部分实现、仅文字设计、需要新增规则。
3. 定义六角格坐标约定、地图方向、cell 尺度、高程单位、地形与对象数据契约。
4. 定义高差规则表：上坡成本、下坡成本、最大可跨越高度、攀爬/跳跃/飞行例外、坠落、近战垂直可达、远程高度射程调整、视线遮挡、高地优势。
5. 决定规则值来自哪里：既有系统配置、世界模组覆盖还是遭遇/场景覆盖。禁止根据奇幻/现代/未来主题硬编码分支。
6. 定义战斗服务端状态生命周期、API 契约、提交事件形状、版本冲突与幂等策略，并明确和 `ACTION-DESIGN.md`、状态/事件层的边界。
7. 编写 ADR/设计文档与阶段验收场景；此阶段只冻结设计，不大规模改代码。

### 交付物

- `TACTICAL-BATTLE-DESIGN.md`（建议名称）：总架构、核心术语、计算契约与非目标。
- 战场、格子、单位、对象与战斗状态 JSON Schema。
- 现有规则复用表和实现缺口表。
- 端到端示例场景：至少有高台、楼梯、墙/掩体、危险区、可交互机关及双方单位。

### 验收

- `tactics` 与 `build` 两个规则引擎有各自适配方案，不要求统一数值公式。
- 每项高度、距离、障碍及环境效果有明确、可测试的规则来源。
- 文档明确哪些信息是世界/故事设定、哪些是权威机制、哪些只是表现资源。

**依赖：** 无。阶段 0 未签定前，不应在前端直接写死战斗规则。

## 阶段 1：六角格战场模型、Schema 与空间查询内核

**目标：** 先做可靠的数据与数学基础，不依赖界面和美术。

### 工作项

1. 新增独立战术空间模块，提供地图创建/校验/序列化/恢复和版本号。
2. 实现六角格邻接、距离、坐标转换、边界判断、层级与 surface 查询。
3. 实现格子、单位、对象、连接和高程数据的结构校验，拒绝重复 ID、非法坐标、悬空引用、无法解释的层级和非法占位。
4. 实现单位占位和 footprint 查询；为大型单位保留多格占位能力，即使首版只启用单格单位。
5. 实现静态的可达性/遮挡/高度查询接口，不直接在其中改战斗资源或伤害。
6. 提供确定性 seed 和小型测试地图 fixture；同一输入和 seed 应生成同样的数据。
7. 增加旧存档的惰性迁移/默认值路径；没有战场字段的旧存档仍应正常载入非战斗玩法。

### 交付物

- 战场模型模块与 Schema。
- `hex_distance`、`hex_neighbors`、`cell_exists`、`elevation_between`、`unit_occupancy` 等纯查询接口。
- Schema 与序列化/恢复测试。

### 验收

- 六个方向邻接对称正确，边界情况与距离边界有自动化测试。
- 不同高度、同一水平投影下的不同层/表面可以共存。
- 不存在的格子与不可通行格子语义不同。
- 坏数据在进入战斗前被拒绝，而不是等战斗运行时才崩溃。
- 原有 ATLAS、PRISM、世界生成及非战斗存档测试不回归。

**并行：** 可与阶段 2 的纯 UI 原型并行，前端先用固定 fixture。

---

## 阶段 2：战场生成、地图模板与最简六角格渲染

**目标：** 玩家第一次能够看见一个六角格战场，即使全部是纯色、线框和符号。

### 工作项

1. 建立场景模板格式，支持不规则地图边界、格子高程、地面类型、墙壁、掩体、垂直通路与对象初始状态。
2. 将 ATLAS 中当前地点/房间、入口、世界类型、场地要素和 seed 作为生成输入；ATLAS 生成世界尺度的拓扑，战场生成器生成战斗尺度六角格。
3. 为生成器添加拓扑和战术约束检查：地图至少可从合法入口到达关键区域、不可把单位放在非法格、不可通行边界不应封死唯一出口，除非场景明确声明如此。
4. 用原生 SVG 实现首版六角格渲染。每格可显示坐标/高度、地形底色、对象符号、单位棋子和选中/高亮状态。
5. 提供缩放、平移、选中单位/格子、格子信息面板；触控目标大小适合手机和平板。
6. 高度差先用最稳妥的可读表现：台阶式高度标记、阴影/色带、立面边线/坡面连接、层级切换或剖面提示。第一版不需要真实 3D。
7. 视图渲染只消费战场快照，不能通过 DOM 结构反推游戏状态。

### 交付物

- 固定地图模板和确定性战场生成器。
- 可交互六角格战场组件。
- 视觉状态约定：选中、可移动、可攻击、不可达、危险、单位阵营、不同高度。

### 验收

- 地图能在桌面与移动浏览器正常显示、缩放和平移。
- 高程层级明显可辨，不靠纯颜色区分一种状态。
- 选择格子能在信息面板查看坐标、高度、地形和对象。
- 正式资产为空时仍能完整显示；无破图图标、无空白崩塌。
- 本阶段可以使用本地测试 fixture，不要求真实战斗已运行。

**并行：** UI、资产占位槽和地图模板可以分工开发，但 Schema 变更必须先协调。

## 阶段 3：移动、路径规划、占位和高度差规则

**目标：** 移动不再只是显示高亮，而是产生经服务端验证的真实战场状态变化。

### 工作项

1. 实现受动作点/移动额度约束的 reachable-cell 搜索；按格子移动成本、高差、地形、状态与移动模式计算。
2. 用 Dijkstra 或适用的路径算法求合法路径；不可把简单直线距离当成移动成本。
3. 实现占位冲突、墙/障碍、地图边界、单位 footprint、狭窄通道和多层地板合法性。
4. 将地面、坡道、楼梯、梯子、绳索、跳跃、攀爬、飞行、游泳等路径转换规则做成可配置规则，不将它们写成前端 if/else。
5. 为高差设置数据驱动的基础规则：上升消耗、下降风险、最大自由跨越高度、攀爬难度、坠落距离/伤害及能力例外。
6. UI 显示合法移动范围、路径、移动成本、攀爬/跳跃提示和危险经过区；在确认前不乐观地改写单位位置。
7. 服务端执行移动后更新权威坐标、行动成本、事件与快照；失败时保持原位置。
8. 移动完成后正确触发进出格子的即时/回合效果（如进入危险区、越过警戒区），但统一触发顺序须在规则文档定义。

### 交付物

- 移动合法性与路径规划 API。
- 高差与移动模式规则表。
- 前端移动预览和确认交互。
- 移动事件及成本记录。

### 验收

- 无法穿墙、穿单位、跨越禁止的高度或瞬移到不连通格子。
- 同样的地图与状态，在服务端计算出一致的可达集合与成本。
- 移动成本可由日志解释，能够说明哪些地形/高差产生了费用。
- 合法移动会改变坐标和状态，非法移动不会；重复提交不会重复扣 AP。
- 攀爬、跌落和飞行等能力不会因为普通移动规则被错误限制。

## 阶段 4：攻击目标、射程、高度、视线、掩体与命中结算

**目标：** 战场几何真正影响现有战斗规则，而不只是一层视觉图形。

### 工作项

1. 统一目标判定接口：目标存在、阵营关系、存活状态、是否可见、是否在距离范围、攻击类型是否允许。
2. 对近战、投射物、远程武器、范围能力和特殊能力定义不同的目标几何契约；不要用一个模糊的“距离够不够”涵盖所有类型。
3. 实现高程参与的距离规则与高度可达判定。近战是否能攻击不同高度的相邻格、射程是否消耗高差额度、飞行目标如何计距，都要由规则配置决定。
4. 实现六角格视线（line of sight）查询：检查射线经过的格子/对象、高度剖面与遮挡；区分阻挡移动、阻挡视线、部分遮挡和透明物。
5. 将战场掩体投影为现有掩体等级/防护修正，并让掩体位置、攻击角度（若规则启用）及是否有遮挡参与判定。
6. 把空间事实适配到 `tactics` 与 `build` 引擎；攻击结算继续使用原规则，禁止在 UI 里计算命中和伤害。
7. 展示可攻击目标、攻击预览（命中条件/射程/遮挡/掩体/高差修正来源）和已结算结果。
8. 命中、擦过、暴击、失手、伤害、抗性、韧性削减、破韧、首领转阶段等现有结果都必须在新界面显示；未使用的复杂规则不能因战棋改造而被丢弃。

### 交付物

- Range / LOS / cover 查询模块。
- 两套规则引擎的战场上下文适配器。
- 目标选择与攻击结果界面。
- 规则说明与逐条回归测试。

### 验收

- 墙体能阻挡规定类型的攻击；低掩体不错误地等同于完全遮挡。
- 高地、低地、层间通道及特殊能力的边界行为可重现、可测试。
- 战术引擎的命中分档、构建引擎的骰池结果与旧有规则测试一致。
- UI 的攻击预览与服务端最终判定一致；攻击结果的关键数值有事件/日志来源。

---

## 阶段 5：场地要素、建筑、道具、障碍与可交互环境

**目标：** 将现有丰富的场地设定从叙事描述升级为能真正改变战场状态的对象，同时保留叙事自由度。

### 工作项

1. 为既有场地要素定义结构化机制字段：对象/区域位置、目标形状、触发时点、交互成本、检定条件、效果、持续时间、使用次数、耐久、状态转换和来源。
2. 将现有六类场地要素（掩体、危险、机关、增幅、情绪、机动）接入通用机制；不另起一套与既有数据表竞争的标签体系。
3. 优先落地具有代表性的最小样本：可移动/可破坏货架、泄漏或带电危险区域、可触发吊物、可攀爬高台、警报机关、可关闭的出口/门、爆炸物或补给点。
4. 实现对象自身的状态机，例如 `intact -> damaged -> destroyed`、`inactive -> armed -> triggered -> cooling_down`、`closed -> open -> locked`。
5. 交互动作统一经过服务器规则和状态提交；破坏对象可能修改占位、视线、路径、危险效果或出口关系。
6. 明确伤害/状态触发时点（进入格、回合开始、回合结束、被攻击、互动成功等），避免同一效果在多个层重复触发。
7. 支持物品拾取与正确库存/任务系统连接；掉落和消耗必须是权威世界事实。
8. 对场地复杂度建立预算与可读性标准，避免每格塞入过多对象导致操作拥挤。
9. 对象的正式图片通过 asset slot 挂载；无图时显示语义图标/几何占位。

### 交付物

- 对象 Schema 与机制注册表。
- 可交互对象动作及事件类型。
- 一张含不少于 5 种不同战术对象的验收战场。
- 既有场地要素迁移/映射表，说明纯叙事条目、可直接执行条目和需设计补充的条目。

### 验收

- 至少一种障碍影响移动、一种对象影响视线、一种掩体影响防护、一种危险造成状态或伤害、一种机关改变战场状态。
- 对象的破坏/触发/拾取结果可保存、可恢复、不会重放重复结算。
- 仍保留其世界与叙事语义；视觉替换不会改变对象的机制定义。

## 阶段 6：战斗生命周期、服务端 API、回合编排与端到端闭环

**目标：** 把规则、空间与界面连成真实可玩的完整战斗，而不是一组可以单独调用的函数。

### 工作项

1. 提供权威战斗启动、查看、动作提交/确认、结束回合、撤退和结束状态等接口。具体路由命名以现有架构审查为准。
2. 所有战斗命令需有版本基线、幂等键/请求 ID、发起角色权限验证和服务端重验；并发或过期操作返回可恢复的冲突提示。
3. 战斗动作按“提出意图 -> 校验 -> 规则结算 -> 状态/事件提交 -> 叙事/前端回执”处理。不要让客户端直接修改状态，也不要绕过项目的权威状态与事件层。
4. 明确玩家行动、敌方自动行动、回合结束、持续效果、反应窗口、连携窗口和胜负检查的唯一时序，保证任意入口都不会漏掉检查点。
5. 将现有 `start_combat()`、`combat_view()`、敌方回合、攻击解算与撤退等函数接入真实会话生命周期；必要时补齐缺少的恢复/序列化行为。
6. 新增战斗视图快照，至少返回棋盘、格子、单位、对象、行动顺序、当前行动者、合法操作提示、事件/日志游标和战场 revision。
7. 战斗期间限制不兼容的自由行动；非战斗玩家/多人事件依现有设计处理，不允许同一份世界状态被战斗和自由行动同时无协调地修改。
8. 实现胜利、失败、全员濒危、单位死亡、撤退、断线恢复、服务端错误等完整状态收尾。
9. UI 能恢复服务端真相：刷新后重新取快照并重画，而不是依赖浏览器内存中的上次棋盘。

### 交付物

- 战斗 API 和状态/事件契约。
- 可从现有游戏流程启动并结束的最小可玩战斗。
- 错误、重试、冲突、断线与恢复 UX。
- API/编排/全链路集成测试。

### 验收

- 能在网页里完整打完一场战斗：启动、选择单位、移动、攻击、敌方回合、胜负/撤退。
- 刷新页面后仍恢复正确单位坐标、AP、资源、对象状态、回合顺序和日志。
- 重复的写请求不会重复扣资源、伤害或奖励。
- `CombatLocked`、权限检查、会话序列和状态提交规则仍然有效。
- 无 AI 配置时，规则、移动和战斗生命周期照常工作，叙事可以降级。

## 阶段 7：有位置意识的敌方 AI 与复杂能力

**目标：** 从“选择一个目标然后攻击”提升为能使用地形与战场对象的战术行为，同时不让 AI 直接操控规则事实。

### 工作项

1. 把敌方行为拆分为意图、候选动作、合法性过滤、效用评分、规则执行和叙事表现六层。
2. 候选动作至少涵盖：移动接敌、拉开距离、攻击、占领掩体、高地争夺、绕行、撤离危险格、使用机制/环境、救援/控制、撤退（由敌人类型决定）。
3. 评分特征包括命中机会、预期伤害、目标威胁、承受风险、地形优势、危险暴露、行动成本、团队协同、个性与当前目标。
4. 复用敌人体型、招式、词缀、行为原型和首领阶段；新增空间行为不得覆盖原有招式表或首领机制。
5. 对路径和攻击候选项只使用公共的移动/射程/视线查询，不要让 AI 自行估算格数或绕开合法性验证。
6. 通过配置限制搜索深度、候选数与耗时；首版可采用规则启发式，不要求通用规划器或每回合调用大模型。
7. 大型/首领单位可以使用多格占位、阶段行为、破坏地形、改变危险区等较复杂行为，但分阶段开启。
8. 将重要决策记录成可检查的结构化原因，方便测试与平衡调整；不必把内部全部评分暴露给玩家。

### 交付物

- 敌方候选动作/评分接口。
- 不同敌人行为原型的数据配置。
- 有障碍、高差、危险区、掩体和多个玩家单位的 AI 测试地图。

### 验收

- 敌人不会尝试明显非法的移动或射击。
- 远程敌人会合理利用距离，近战敌人能够寻找合法接敌路径，控制型敌人会使用场地或控制能力（取决于设定）。
- 遇到高差、阻挡和危险地形时，行为会改变，而不是忽略地图。
- AI 故障或超时有确定性退路，不会卡住整场战斗。

## 阶段 8：存档兼容、多人同步、可见性与事件重放

**目标：** 确保战斗不仅能单机演示，而且可长期运行、多人参与及安全恢复。

### 工作项

1. 定义战场及战斗快照版本、迁移规则和缺省值。旧存档没有战术棋盘时继续支持旧玩法。
2. 将单位位置、对象状态、随机/规则结果、当前回合、行动资源、临时效果和事件游标纳入保存与恢复。
3. 使用项目权威状态/事件机制记录战斗行动；战斗事件至少包含动作 ID、行动者、目标/对象、规则引用、成本、空间变化、效果与提交版本。
4. 支持从基线快照加事件恢复，明确哪些字段来自角色权威状态，哪些是战斗临时状态，避免双写漂移。
5. 多人局中对单位控制权、回合推进、暂停/房间状态、并发命令和 PvP 规则使用现有权限模型。
6. 依项目的私密信息约束控制可见性；若引入战争迷雾，需区分真实世界状态与各玩家可见投影，不能把隐藏敌人的完整状态直接发送给客户端。
7. 事件重放必须复用已记录的权威骰点和结果，不能重掷后生成不同战斗。
8. 对断线、双端登录、重复命令、旧 revision、战斗中切场景及并发状态变化做恢复测试。

### 交付物

- 存档迁移与版本策略。
- 战斗事件清单和恢复流程。
- 多人权限/同步测试与故障注入测试。

### 验收

- 已保存的战斗能够恢复到同一空间和规则状态。
- 已提交的事件重放不重复应用伤害/奖励。
- 并发命令不会令两个玩家同时消耗同一份 AP 或覆盖彼此的位置。
- 不泄漏玩家权限以外的隐藏角色/对象状态（若该模式已启用）。

## 阶段 9：视觉资产、动画反馈、无障碍和性能优化

**目标：** 在战斗玩法稳定后提高可读性和完成度，不把视觉开发变成规则开发的前置依赖。

### 工作项

1. 使用现有主题 token 做三世界主题的通用配色和样式：奇幻、现代、未来使用一致的空间语义，但可以有不同边框、纹理、对象图标和动画风格。
2. 将角色、敌人、地形、建筑、掩体、机关、危险和道具连接到受控 asset manifest，正式资产缺失时继续使用占位符。
3. 按项目现有 `@promptor` / `@builder` 分工：`@promptor` 产出提示词和素材清单文档，外部模型离线生成并经审核后入库；`@builder` 接入路径与加载逻辑，不在代码里伪造“已有素材”。
4. 先做影响战术可读性的反馈：移动路径、攻击预览、命中方向、伤害数字、状态变化、环境触发、危险提示和回合提示；装饰性粒子效果后置。
5. 高程显示要让玩家理解平台、坡道、下层和遮挡，避免仅靠俯视色块导致高度误读。
6. 支持键盘、鼠标和触屏；状态同时使用形状/标签/图标，不只靠颜色。
7. 对地图规模进行性能测试；中小型地图可先用 SVG。只有测试显示 DOM/SVG 更新确实成为瓶颈，才引入 Canvas 或其他渲染技术，且点击/焦点/无障碍语义要有配套方案。
8. 优化移动端布局：地图可缩放平移，操作按钮有足够热区，目标选择和动作详情使用抽屉/底部面板，不强行压缩桌面多栏界面。

### 交付物

- 正式资产槽位及提示词清单。
- 桌面与移动战斗 UI。
- 性能预算、无障碍清单和视觉回归测试。

### 验收

- 缺少正式图片时仍可完整游玩；图片失败会回退，不阻塞行动。
- 目标、可移动范围、障碍、掩体和高程在不同主题及明暗模式下均可辨识。
- 移动端核心操作不被面板、键盘或缩放手势卡死。
- 性能问题有基准数据证明，不因追求技术时髦提前复杂化渲染堆栈。

## 阶段 10：平衡、内容扩充与规则完整性审计

**目标：** 保证六角格不会让既有战斗内容退化，同时让高度差和场景交互有足够深度。

### 工作项

1. 为三个主题各建至少一张代表地图：奇幻（城墙/高台/魔法危险）、现代（车辆/建筑/掩体/警报）、未来（垂直通道/能量屏障/设备/环境危害）。这些应是同一战场机制系统的数据，不是三套硬编码系统。
2. 每种地图至少展示：高低平台、上下通路、不可通行障碍、视线遮挡、不同档位掩体、危险区、机关、可互动对象和可结束战斗的目标。
3. 检查现有规则逐项映射：失手、擦过、暴击、抗性、减益、韧性、破韧、首领阶段、连携、状态恢复、动作成本、反应窗口、撤退与遭遇预算。
4. 为不适合直接在六角格表达的规则制定语义映射（例如抽象距离、社会战斗、群体遭遇或极大规模战斗）；不得无声地删除。可保留抽象模式，但必须明确什么时候使用、如何与地图模式切换。
5. 建立固定 seed 的遭遇回放和平衡数据；统计单位行动数、平均回合、胜负、移动选择、环境互动使用率与规则边界错误。
6. 对地图生成增加属性测试：可达性、入口/出口、单位合法部署、高度连接、对象关联、随机性复现和场地要素密度。
7. 完成 GDD、规则数据、Schema、代码和用户界面的一致性审计。

### 交付物

- 三个主题的示例战斗内容。
- 规则完整性追踪表及差异列表。
- 确定性战斗回放与平衡测试。
- 发布候选版本的缺陷清单。

### 验收

- 现有机制没有因为六角格转型被悄悄简化或丢失；不支持的规则有明确的后续计划和回退路径。
- 三个世界主题可以共享引擎，但外观、地形组合、对象和世界特则有各自的内容表现。
- 手工地图和生成地图都能通过相同的规则校验。
- 一场典型遭遇可以完整执行、存档、恢复、回放和复盘。

## 5. 关键规则设计建议

### 5.1 高度差必须是规则，不是装饰

- 采用离散高程层，允许一格存在多个明确表面/楼层。
- 移动、攻击和视线使用同一份高程事实；界面显示不能与服务端计算采用不同高度。
- 高度差具体效果由数据配置：上升移动成本、自由跨越上限、攀爬动作、下降风险、坠落损伤、近战可达范围、远程射程和视线阻挡。
- 高地加值应复用现有战斗规则或通过设计审查新增配置，不要在多处重复加值。
- 需要支持桥下/桥面、楼上/楼下、屋顶、悬崖和飞行单位；不要求首版全部开放，但数据结构不能封死这些能力。

### 5.2 空间计算应该是统一服务

统一对外提供：

- 六角格距离；
- 合法移动范围与最小成本路径；
- 单位/物件占位；
- 高差、攀爬连接与可达性；
- 目标距离与攻击合法性；
- 视线、遮挡、掩体与高度优势；
- 环境触发范围和伤害/状态覆盖。

任何 UI、敌人 AI 或战斗规则适配器都应调用这些接口，不得分别实现一份不一致的算法。

### 5.3 物理精确度按规则需要控制

首版采用离散格子和规则判定，不实现实时碰撞物理。移动在动作提交时完成，动画只表现结果。推、撞、击飞、爆炸、坠落等效果以明确的空间变换和规则事件处理，避免因为客户端动画时序影响权威结果。

### 5.4 叙事与机制并行，但事实单一

例如“高压电源被水导通”这类效果：

- 世界/场景内容提供物件描述与设定；
- 对象数据声明带电状态、水面范围及触发规则；
- 规则层结算实际目标、伤害、状态和对象变化；
- 叙事模块基于已提交事实生成描述；
- 前端展示同一状态变化。

不能让 AI 叙述中说“警报关闭了”，但真实对象状态仍然是开启的。

## 6. Issue 拆分和执行策略建议

实际开始研发时，建议按阶段创建 Issue，每个 Issue 具有明确文件范围、依赖、非目标、测试命令与验收标准。

建议的任务组：

1. **设计单独立完成**：阶段 0。先审查/定稿战场 Schema、高差规则、空间接口与 API 状态契约。
2. **数据与纯函数轨**：阶段 1，可并行准备测试 fixture 和迁移测试。
3. **前端原型轨**：阶段 2 的 SVG 棋盘、移动端交互和占位符；依赖固定 Schema，不能自定规则。
4. **空间/战斗后端轨**：阶段 3–6，按照依赖顺序串行集成；路径、高度、视线、结算与状态提交不要交给多个 Agent 同时修改同一核心文件。
5. **环境对象轨**：阶段 5 可在 Schema 冻结后分对象类型并行，但必须共享一个机制契约。
6. **AI 轨**：阶段 7 等空间查询和行动合法性稳定后开始，不应提前让 AI 假定未来接口。
7. **恢复/平衡轨**：阶段 8–10，可在端到端切片稳定后并行做测试、用例与内容数据，但 Schema 变化需先通知依赖方。

每个 Issue 需要附带：

- 目标与用户可见结果；
- 依赖的设计文档/Issue；
- 允许修改和禁止修改的文件/职责范围；
- 使用的规则/数据来源；
- 必须运行的测试；
- 可观察的验收证据；
- 明确的非目标，避免一次任务扩成整场重写。

不要一次性把所有阶段交给一个 Agent 无边界实现。适合采用“设计审查 -> 小切片实现 -> 自动测试 -> Master Agent 代码/行为审查 -> 修复 -> 合并 -> 下一切片”的节奏。若采用单会话自动执行，也应以每个阶段的可验证检查点作为停靠点。

## 7. 测试策略总表

| 层级 | 必要测试 |
|---|---|
| Schema/迁移 | 必填字段、非法格/高程/引用、重复 ID、旧存档载入 |
| 六角格数学 | 六邻接、距离边界、坐标映射、地图边界、不同层/表面 |
| 移动 | 路径成本、障碍、占位、高差、攀爬、飞行、危险格、重复提交 |
| 射程/视线 | 距离边界、目标高度、墙体遮挡、透明/部分阻挡、掩体等级 |
| 战斗规则 | 两个引擎原有边界与回归、伤害、抗性、韧性、状态、首领、连携 |
| 对象交互 | 状态机、耐久、触发时点、范围效果、奖励/拾取、重复动作幂等 |
| AI | 合法动作、可达性、地形利用、固定 seed、超时和退路 |
| 集成 | 开战到胜负全流程、旧存档、刷新恢复、事件重放、多用户并发 |
| UI | 桌面/平板/手机、键鼠/触屏、缩放、可读性、无图回退、无障碍 |
| 生成与平衡 | 固定 seed 可复现、入口可达、部署合法、不同地形与难度分布 |

## 8. 第一版可玩标准（MVP）

在把工作扩展到全部内容之前，先完成一个包含以下内容的单场遭遇：

- 1 张不规则六角格地图；
- 至少 3 个高程层级；至少一处楼梯/坡道或攀爬连接；
- 墙体/不可通行障碍、轻/中/重掩体中的至少两类；
- 1 个危险区域；1 个可触发机关；1 个可破坏或可移动对象；
- 2–3 个玩家单位与至少 2 类敌人；
- 移动、近战攻击、远程攻击、至少一种能力、环境互动、敌方自动回合、撤退和胜负结算；
- 攻击分档、抗性/状态、韧性/破韧以及至少一种首领或特殊敌人机制通过已有规则接线体现；
- 保存、刷新恢复和事件/日志；
- 原生 SVG/几何图形版本即可，无正式美术要求。

如果这一场战斗不能可靠运行，不建议先扩大地图、美术或敌人数量。

## 9. 最终实施顺序与优先级

| 优先级 | 阶段 | 为什么 |
|---|---|---|
| P0 | 0 规则和架构定稿 | 不先统一高差、射程和双引擎契约，后续会返工 |
| P0 | 1 六角格数据与空间内核 | 所有战斗操作和视图都依赖同一空间真相 |
| P0 | 2 最简地图渲染 | 先有可见棋盘，才能验证交互与可读性 |
| P0 | 3 移动与高差 | 六角格战棋的基本操作，也是地图存在的主要理由 |
| P0 | 4 攻击/射程/视线/掩体 | 空间必须真实影响现有战斗规则 |
| P0 | 6 战斗生命周期集成 | 把现有引擎接成可玩闭环；可在阶段 2–4 中提前铺 API 契约，但最终全链路验收在此完成 |
| P1 | 5 环境对象/障碍/机关 | 决定战场是否有战术深度，而非只是一张棋盘 |
| P1 | 8 存档/多人/事件回放 | 长期项目与多人体验的可靠性要求 |
| P1 | 7 敌人战术 AI | 依赖可靠的位置、路径、射程和目标合法性接口 |
| P2 | 9 视觉资产与体验优化 | 规则先稳定，素材后接入，降低返工 |
| P1 发布门槛 | 10 规则完整性与内容平衡 | 确保新地图没有削弱 NotDND 的既有设定与复杂度 |

注意：阶段 5、6、7 的编号是为表达工作内容，不代表所有开发都必须严格等待前一阶段完成。例如，战斗 API 合同应在阶段 0 定稿，API 骨架可以在阶段 1 后提前开发；但环境效果和敌人 AI 必须依赖稳定的空间合法性及结算接口。
